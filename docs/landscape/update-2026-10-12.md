## 7. What a full-size validation on Kaggle would need (described, not launched)

The other agent's harness (`VALIDATION`, `STRICT`, stage monitor; `reviews/diag67-2026-10-12.md`) runs a
notebook on a train-derived validation set of test size as if it were the scoring rerun and reports MRR per
table. For a patch to e006's chain the run would be:

1. **One notebook, three tables.** e006r unchanged (control), and the patched overlay executed after it on the
   same run's objects, exactly as flexonafft's last cell does ("Save an exact E006 control"): the overlay costs
   seconds, so the base chain (estimated 3 h 40 min on the hidden set) runs once. Mode `E006_BASE='e006'`,
   which reproduced e006r on 399 of 400 rows.
2. **Assertions** (`STRICT`): the control table equals a stored e006r table of the same input; the patch
   changes at least one row (flexonafft's "NO-OP versus E006" guard); every stage reports healthy; no stand-in
   table can be written (`E006_BASE_ON_FAIL='fail'`).
3. **Readout**: per molecule reciprocal rank of control and patch, paired difference ± SE, wins / losses,
   answers in / out, by adduct class and `lib_max` band; the purge mode must hold the validation structures out
   of the library *and* accept that `fpnet_full1`, the public ranker and the simulators have seen them
   (pitfall 10): the control's validation MRR will sit far above 0.443, and only the paired difference is
   usable, with the caveat of section 6.2.
4. **Gate before a submission** [C, my proposal]: paired difference at least 2 SE **and** at least +0.008 in
   the masked local arm or the validation run, **and** no public pair of the same change at or below its
   control. None of today's three patches passes the last condition.
5. Cost: one GPU session of about 4 h per run; one submission per candidate afterwards (a resubmission adds
   nothing, section 5.1).
