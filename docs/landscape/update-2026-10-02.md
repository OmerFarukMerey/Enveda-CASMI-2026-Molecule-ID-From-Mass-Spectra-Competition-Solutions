### 2.2 The CPU run of v29: 0.411 against 0.393 for the same code

Facts [V]:
- `scratch/landscape2/diffs/imranarif536_...__vs_v29.txt`: the only change against `scratch/wph/code.py` is

  ```
  -IS_RERUN = bool(os.getenv('KAGGLE_IS_COMPETITION_RERUN')) or _sig != '654e030e4173780e945252b4a5adf70b'
  +IS_RERUN = True
  ```
  At scoring time both are true, so the scored code is v29.
- Its inputs are the 13 reference datasets plus `dmitriigluzdov/casmi26-pubchem-popularity-prior`. The log prints
  `v17 popularity prior 0.25 200 /kaggle/input/casmi26-pubchem-popularity-prior`.
- `kaggle kernels logs` (`scratch/landscape2/logs/imran.log`), full run on the 400 visible molecules, 15,667 s in total:
  - `fp models: 1 single + 1 merged on cpu`, `[ice] cuda unavailable -> cpu`, `[gl] cuda unavailable -> cpu`. The metadata says
    `enable_gpu: true`, yet no GPU was usable in that session.
  - ICEBERG: `status budget {'n_mols': 400, 'n_mols_covered': 371, 'n_mols_scored': 90, 'n_cands': 26186, 'n_scored': 5679}`,
    2.46 predictions/s (a T4 does about 40). **ICEBERG scored 90 of 371 molecules.**
  - v29 feeds ICEBERG in the order `mids = sorted(BASE, key=lambda m: BASE[m][2])`, that is by `lib_max` ascending ("molecules
    without a library-level match first"). The 90 scored molecules are those with the weakest library match.
  - GLACIER finished on CPU: 366 of 366 `[M+H]+` molecules, 3,265 s.
  - `ICE rerank stats {'molecules': 90, ...}`, `GL rerank stats {'molecules': 88, ...}`: the first re-rank (base list and PubChem
    list, before the merge) happened for 90 molecules only, because it requires ICEBERG scores.
  - `fused (+ICE) submission written; top-1 changed in 7 | ICE reordered 365`: the post-fusion re-rank ran for 365 molecules,
    for 275 of them with GLACIER alone.
- The notebook is third in the score order, above our 0.409 notebook. The author's team went from 0.384 (10-01 21:23) to 0.411.
  Every other copy of this code that ran on a GPU sits at 0.393 or lower (section 2.1; haideptry v32 is 17th in the order).

Reading [U]: with a GPU the pipeline applies ICEBERG + GLACIER twice to every covered molecule (before the PubChem merge and
again after the engine fusion). In the CPU run 76% of the molecules, those with the stronger library matches, got no ICEBERG at
all, no forward re-rank before the merge, and one GLACIER-only re-rank after the fusion. If the 0.411 belongs to this version,
that restriction is worth about +0.018 over the full configuration (2.3 public-LB molecules; one submission has a standard error
of about 0.016, so this is one observation, not a measurement).

What is not established [U]:
- The notebook is at version 3. The CLI cannot show which version carries the score. Versions 1 and 2 may have had other code.
- Whether the scoring rerun also had no GPU. It uses the accelerator saved with the version; the commit log is the only evidence.
- Whether the 15 teams at 0.411 are the same thing. Seven of them reached 0.411 on 10-01 between 09:56 and 14:17 UTC, before this
  notebook existed, so at least those have another source.
- Our v4a (ICE/GL weight 0 at `lib_max ≥ 0.9`) changed nothing (0.404 = 0.404). The CPU run cuts much lower: only the weakest
  quarter by `lib_max` keeps ICEBERG.

A second v29 copy also ran on CPU ([yufotest](https://www.kaggle.com/code/yufotest/casmi26-v29-baseline), smoke run, log shows
`cuda unavailable`), but that team has not submitted since (still 0.328). [V]

- hengck23's demo and dataset: embed a spectrum with the DreaMS embedding model, cosine kNN against pre-computed embeddings of
  MassSpecGym (231k spectra). Class 1 only by the author's own words (forum 744893). No fingerprint head, no re-ranking.
- haideptry v40: the first spectrum of each molecule → top-20 neighbours → their SMILES as a third list in the reciprocal-rank
  fusion (`ALPHA, BETA, KRR = (0.65, 0.35, 3.5)`), only when `lib_conf < 0.6`. No mass filter, so most neighbours have the wrong
  mass. Scored below v38.
- haideptry v41: neighbours kept only within ±10 ppm of the neutral mass, at most five, appended after the fused list.
- The "Standalone Benchmark CV": 100 enveda-np-examples molecules from `train.parquet` queried against MassSpecGym. A hit means
  the same structure has a MassSpecGym spectrum. The 0.562 is a class-1 retrieval number, lower than the 0.93 the
  library search already gets for class 1, and says nothing about held-out structures.
- Nobody public uses DreaMS for fingerprint prediction or for re-ranking candidates.

**Weights and training data** [V: Bushuiev et al., Nat. Biotechnol. 2025, full text via Europe PMC PMC13090125, saved as
`scratch/landscape2/web/dreams_fulltext.xml`; repository README; Zenodo 10997887]:
- Pre-training: self-supervised on GeMS, unannotated spectra mined from MassIVE GNPS. No library labels.
- Embedding model (`embedding_model.ckpt`): contrastive fine-tune on a refined MoNA subset (about 25,000 spectra, 5,500
  connectivity blocks). The Methods state that they "do not use any spectra from NIST20 for training"; NIST20 serves as the
  evaluation set. **NIST: no.**
- The other fine-tuned heads (fingerprints, properties, fluorine) are trained on splits of MoNA and NIST20 together.
  **NIST: yes. Do not use those heads.** The DreaMS Atlas also contains NIST20 nodes.
- Licence: code MIT, Zenodo weights CC BY 4.0.
- hengck23's file is a state dict "ported from" the Hugging Face space of the authors. I did not compare hashes with Zenodo. [U]

**Are the gains real?** No. The only scored DreaMS notebook is below its base; the titles "Champion" are copies; hengck23's own
team is at 0.071 with retrieval alone. The public reference set (MassSpecGym) is a subset of the public libraries that
`train.parquet` already contains, so retrieval against it cannot add class-2 or class-3 answers. [V for the scores, U for the
overlap statement]

Where DreaMS could still help us, without public evidence [U]: as an analog-similarity signal for class 2 (megayak measured a
tie with the mass-shifted search), or as an extra feature for a ranker we train ourselves. Both need our own held-out
measurement and a ranker retrain. Runtime is not an issue (model load plus 12 molecules: 30 s on a T4, log of v40).
